## 两个账户的职责

|账户|角色|配置位置|
|---|---|---|
|A：现有应用关联的 Sandbox Business 账户|账本读取它的交易；本次在 PayPal 页面由它付款|现有 `.env`，保留原值|
|B：第二个 Sandbox Business 账户|测试商家，接收 A 的购买付款|单独 `.env.sandbox-checkout`|

已经查询到的商家收款和退款不能冒充 A 的购买消费。付款页面不能使用 B 给 B 自己付款；以前另一个 Personal 买家的消费也不等于可读取 A 的消费。账户能否完成此次付款，还要以沙箱实际响应为准。

## 配置第二个应用

1. 打开 https://developer.paypal.com/dashboard/applications ，选择 Sandbox。
2. Create App，名称可用 `Listening Ledger Test Store`。如果提供 Type，选择 Merchant。
3. Sandbox Account 选择第二个商家 B，确认与 A 不同。创建应用，复制其 Sandbox Client ID 和 Secret。
4. 在项目根目录打开 `.env.sandbox-checkout`，填写下面两行；不要发到聊天，不要覆盖原 `.env`。

```env
PAYPAL_TEST_MERCHANT_CLIENT_ID=
PAYPAL_TEST_MERCHANT_CLIENT_SECRET=
```

第二个应用只负责本次测试结账，不需要为了它重新更换 A 的查询凭据。第一版主账本仍然只查询，不增加付款按钮。

## 开始测试

在项目根目录运行：

```powershell
node scripts/sandbox-checkout.mjs
```

打开 http://localhost:4335/ 。启动服务或打开首页不会调用 PayPal。

1. 点击“创建 USD 12.00 沙箱测试订单”。这时才用 B 的凭据创建订单，尚未收款。
2. 点击“前往 PayPal Sandbox”，在 `www.sandbox.paypal.com` 页面登录 **A 的沙箱登录邮箱和密码**。不要输入 Developer 真实账号密码。若自动登录成 B，请退出并换成 A。
3. 在 PayPal 页核对金额 USD 12.00、测试商家，手动批准。遇到取消、风控或账户限制，不绕过、不换到 Live；保留错误信息再排查。
4. 返回本地页后，点击“核验批准并完成这笔沙箱付款”。服务器先查询该订单，核对 ID、购买关联、币种、金额，以及实际付款账户是否与查账账户 A 相同，再对 APPROVED 订单执行 capture。原查账服务（4333）需保持运行，且已有成功同步的账户快照。付款人缺失或不匹配会阻止收款；不要把返回 URL 中的 PayerID 当作核验依据。返回页面本身不是成功证据。
5. 只有结果为 COMPLETED 且核对金额一致，才显示成功及 Capture ID。结果不明确时重试同一入口；不要另建订单。本工具只处理一笔当前测试订单；符合恢复条件的旧订单保留归档，完成后再次操作不会新建付款。
6. 回 http://localhost:4333/ → 账本来源 → USD，查询包含本次日期和现有限额周期的范围。观察购买事件、支出方向、已完成状态，再检查书页与限额计算。

报表可能延迟出现，因此刚付款后没有返回记录不代表付款失败。若只看到 B 的收入，需要核对主应用是否仍关联 A；不能改金额符号、把退款当购买或用示例覆盖查询结果。等查询确实出现 A 的有效支出后，再做 AI 分类、人工确认和刷新恢复。

## 中断与数据

- PayPal“取消”返回不会调用 capture。
- 中断后重开辅助页，订单仍在独立 `data/sandbox-checkout.sqlite` 中；请求幂等 ID 一并保存。
- capture 结果不明确时，下次先查询同一订单；已经完成则恢复结果，不重复发起 capture。
- 创建订单的结果不明确且超过五小时，工具停止自动重试，要求人工核查，避免超过安全窗口后生成新订单。
- 辅助页仅监听 127.0.0.1:4335，禁止跨来源表单和未创建订单；凭据只在服务端读取，不发送到网页。不支持 Live、退款或任意金额。
- `.env.sandbox-checkout` 与 `data/` 已被 `.gitignore` 排除，不能纳入源码发布。当前发行脚本的显式白名单还不包含辅助脚本和该配置模板，正式打包前需由开发者选择是否将开发辅助工具一同交付。

## 官方依据与验证边界

- [Orders v2 创建](https://developer.paypal.com/api/orders/v2/orders-create)：CAPTURE 意图、付款来源体验配置、PayPal-Request-Id。
- [订单查询](https://developer.paypal.com/api/orders/v2/orders-get)：以服务端查询的订单状态和金额为依据。
- [订单 Capture](https://developer.paypal.com/api/orders/v2/orders-capture)：买家批准后服务端收款。
- [交易事件码](https://developer.paypal.com/reports/reference/t-codes/)：同一购买事件对于买家和卖家的收支方向不同。

这些是接口实现依据，不保证当前账户可以付款，也不替代真实沙箱测试。不要在提交材料里把本工具的模拟测试写成实际 PayPal 付款已完成。
